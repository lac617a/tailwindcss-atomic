## Next.js 15 (App Router, Tailwind 4)

```ts
// next.config.ts
import {withTailwindcssAtomic} from "tailwindcss-atomic/next";

const nextConfig = {reactStrictMode: true};

export default withTailwindcssAtomic(nextConfig);
```

Mantén PostCSS con `@tailwindcss/postcss` **y después** `tailwindcss-atomic/postcss`.

<Callout>
  Los wrappers que devuelven una **función** de config de Next (`withPostHogConfig`, Sentry, algunos setups de `next-intl`) hay que invocarlos, no hacerles spread. `withTailwindcssAtomic` ahora resuelve esas funciones para no perder tu `webpack()` (fallbacks de `dns`/`net`/`tls`). PostHog sigue queriendo ser el wrapper **más externo**:

  ```ts
  export default withPostHogConfig(
    withTailwindcssAtomic(withNextIntl(nextConfig), {report: true}),
    { /* posthog */ },
  );
  ```
</Callout>

## Next.js 15 + Tailwind 3 + SCSS

Tailwind v3 no expande `@use 'tailwindcss/utilities'`; espera `@tailwind utilities`. Si la entrada es SCSS (por ejemplo `scss/styles.scss` importada desde `app/layout.tsx`) el warmup **normaliza** esas capas y, si está instalado `sass`, compila los `@use` locales antes de PostCSS. Así el mapa `flex` → `_xxxxxx` existe **antes** de que Webpack transforme los bundles de App Router (client, SSR y RSC).

```scss
// scss/styles.scss
@use 'tailwindcss/base';
@use 'tailwindcss/components';
@use 'tailwindcss/utilities';
@use './themes/brand' as themes;
```

```ts
// app/layout.tsx
import "../scss/styles.scss";
```

```js
// postcss.config.js — el plugin atomic va el último
module.exports = {
  plugins: {
    "postcss-import": {},
    "tailwindcss/nesting": {},
    tailwindcss: {},
    autoprefixer: {},
    "tailwindcss-atomic/postcss": {},
  },
};
```

```ts
// next.config.ts
import {withTailwindcssAtomic} from "tailwindcss-atomic/next";

export default withTailwindcssAtomic({reactStrictMode: true});
```

`withTailwindcssAtomic` inyecta el loader de Webpack (pre) y el plugin que, en `processAssets`, atomiciza **todo** el CSS y después reescribe **todo** el JS (incluidos chunks de servidor). En `next dev` invalida módulos JS cuando cambia el mapa.

El path clásico `app/globals.css` con `@tailwind base/components/utilities` sigue igual.

## Next.js 15.5+ / 16 + Turbopack

```ts
// next.config.ts
import {withTailwindcssAtomic} from "tailwindcss-atomic/next";

export default withTailwindcssAtomic({
  reactStrictMode: true,
});
```

```json
{ "scripts": { "dev": "next dev --turbopack --port 3019" } }
```

`withTailwindcssAtomic` rellena `turbopack.rules` con el loader de TS/JS (además del hook de Webpack). En Next 16.3+ las reglas son un array con `condition: "foreign"` y `condition: { not: "foreign" }`; el shorthand `{ foreign, default }` ya no pasa la validación. El PostCSS de Tailwind 4 sigue siendo obligatorio.

## Turborepo / monorepo (Next + Turbopack)

Un className mixto (`flex … hover:bg-revamp-… _cafc46 _ffc2a9`) significa que **el CSS sí se atomicizó** pero **parte del JS no se reescribió**. En Webpack el plugin recorre todos los chunks en `processAssets`. Turbopack no tiene ese paso: solo reescribe los módulos que pasan por el loader.

Eso pasa cuando el `cva()` / `cn()` vive en un design system fuera de la app (`packages/ui`, `node_modules/ui-latamwin`) y las reglas de Turbopack solo tocaban el código de `apps/webs/latamwin`.

`withTailwindcssAtomic` ahora:

1. Pone el loader en **`turbopack.rules`** para `*.ts(x)`, `*.js(x)`, `*.mjs` y `*.cjs` como un array de dos reglas: `condition: "foreign"` (node_modules / workspace) y `condition: { not: "foreign" }` (código de la app). El loader no-op en `react` / `next`; sí reescribe `transpilePackages` y junctions del workspace.
2. Fija `turbopack.root` y `outputFileTracingRoot` en la raíz del monorepo (`turbo.json` / `pnpm-workspace.yaml`) si no los definiste.
3. Añade a `transpilePackages` los paquetes del workspace que la app declara en `dependencies`.
4. Hace warmup de **todas** las entradas CSS que encuentre (no solo la primera). Puedes forzar la de la web:

```ts
// apps/webs/latamwin/next.config.ts
import {withTailwindcssAtomic} from "tailwindcss-atomic/next";

const nextConfig = {
  reactStrictMode: true,
  transpilePackages: ["ui-latamwin"],
};

export default withTailwindcssAtomic(nextConfig, {
  cssEntries: ["scss/styles.scss"],
});
```

<Callout type="warning">
  Si un paquete UI se publica como `dist/*.js` y no está en `transpilePackages`, sus strings `flex` / `bg-*` llegan intactos al DOM y se mezclan con los hashes de la app. Añádelo a `transpilePackages` o importa el source (`exports` → `src`).
</Callout>

**No** hashees ese `dist` del UI en Rollup (`preserveModules` debe dejar las utilidades originales). **No** pases `{ library: true }` a `withTailwindcssAtomic` en la app Next: esa opción es solo para el Rollup del design system, y el adapter de Next la ignora.

Si en el DOM está `bg-opacity-50` y no hay `background-color`, `twMerge` v3 tiró `bg-neutral-300`. Usa `bg-neutral-300/50`. Ver [Conservar y runtime](./preserve).

## Vite (Tailwind 4)

No hace falta `tailwind.config.js`. La entrada CSS usa `@import "tailwindcss"` (y opcionalmente `@theme`).

La forma recomendada con Vite es `@tailwindcss/vite`. **No** hace falta `@tailwindcss/postcss` ni `postcss.config`:

```ts
// vite.config.ts
import {defineConfig} from "vite";
import react from "@vitejs/plugin-react";
import tailwindcss from "@tailwindcss/vite";
import tailwindcssAtomic from "tailwindcss-atomic/vite";

export default defineConfig({
  plugins: [react(), tailwindcss(), tailwindcssAtomic()],
});
```

Si prefieres PostCSS en vez del plugin de Vite:

```js
// postcss.config.mjs
export default {
  plugins: {
    "@tailwindcss/postcss": {},
    "tailwindcss-atomic/postcss": {},
  },
};
```

```ts
// vite.config.ts
import {defineConfig} from "vite";
import react from "@vitejs/plugin-react";
import tailwindcssAtomic from "tailwindcss-atomic/vite";

export default defineConfig({
  plugins: [react(), tailwindcssAtomic()],
});
```

## Vite (Tailwind 3)

```ts
import {defineConfig} from "vite";
import react from "@vitejs/plugin-react";
import tailwindcssAtomic from "tailwindcss-atomic/vite";

export default defineConfig({
  plugins: [react(), tailwindcssAtomic()],
});
```

El PostCSS de v3 va **después** de `tailwindcss` y `autoprefixer`.

## Astro (Tailwind 4)

Astro usa Vite. Tailwind v4 va con `@tailwindcss/vite` (no `@astrojs/tailwind`). La integración `tailwindcss-atomic/astro` inyecta el rewrite de `class` en `.astro`, JS extraído y CSS:

```ts
// astro.config.ts
import {defineConfig} from "astro/config";
import tailwindcss from "@tailwindcss/vite";
import tailwindcssAtomic from "tailwindcss-atomic/astro";

export default defineConfig({
  integrations: [tailwindcssAtomic()],
  vite: {
    plugins: [tailwindcss()],
  },
});
```

```astro
---
import "../styles/global.css";
---
<div class="flex p-6">Hola</div>
```

Si prefieres no usar la integración, el plugin de Vite hace lo mismo:

```ts
import tailwindcssAtomic from "tailwindcss-atomic/vite";

export default defineConfig({
  vite: {
    plugins: [tailwindcss(), tailwindcssAtomic()],
  },
});
```
